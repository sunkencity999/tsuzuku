# TSUZUKU — 09 · Frame protocol (manual)

**Status:** protocol defined; **no manual run recorded yet**. A headless CDP stand-in (not the manual DevTools protocol; §6) was recorded on 2026-10-18 and fills two rows of §5 — it fails the 18 ms frame line everywhere and the manual run is still owed. Companion to design 09 §10 (budgets, "Frame budget" row), §6.4 (the wipe; footnote ⁴'s brush-edged `mask-image` experiment ships only if it passes this protocol), §6.7 (performance rules) and §12.1 decision 10 (DevTools 4× CPU throttle is the stand-in for a mid-range Android; no device; A2 and C2 run it before Phase C closes). Nothing in the repo measures frames — `src/styles/motion.test.ts` guards *what* animates, not how fast it paints — so this file is the measurement, by hand, and the only place results are recorded besides each PR's checklist line.

The pass line is the spec's, uncalibrated against a real device (§12 question 10): **during a transition, no main-thread frame over 18 ms and no long task over 50 ms.** A run that fails is recorded as a fail with the numbers; the table below never carries a number nobody measured.

## 1. Setup checklist

- [ ] **Browser.** Chrome stable (same-document View Transitions ship from Chrome 111; the `::view-transition-*` rules in `motion.css` are attached selectors, §12.1 decision 12). Note the exact version in the results row. The protocol measures Chrome only (the DevTools *Frames* lane and the 4× throttle are Chrome's); an engine without `document.startViewTransition` — Safari < 18, Firefox < 144, §6.4's fallback condition, feature-detected by `viewTransitionApi()` in `src/app/transitions.ts`, never by engine name — takes the `fallbackEnter()` nijimi path and is out of scope. Current Safari and Firefox run the View Transitions and could be measured with their own tools; nothing here records them.
- [ ] **Build.** The production build served locally (`npm run build && npm run preview`, or the GitHub Pages deploy of the commit under test) — never the Vite dev server, whose unbundled modules and HMR client change the main-thread profile. Record the commit hash.
- [ ] **Fonts and shell warm.** Load the app once, wait for the service worker to install (DevTools → Application → Service workers shows *activated*), then reload. The first-paint fonts (`DotGothic16-base`, `YujiSyuku-shell`, `ShipporiMinchoB1-shell`) and `calendar/koyomi.json` must come from the cache so the trace measures paint, not network.
- [ ] **Save.** A learner with something to draw: ≥ 30 days trained, a lit or gold flame, two or more forgiveness chips, a few stamps and badges, at least one station reached. (A fresh save renders an emptier Dojo and a shorter Road and would pass too easily.) Export it first (Settings → Backup) so the run is repeatable.
- [ ] **Settings.** Reduced motion **off** in the app (Settings) and at the OS (the protocol measures the full motion; a second, optional pass with reduced motion on is a control and must be labelled as such). Theme: run the ten turns once in Dojo Morning and once in Arcade Night; glows exist only in Night (§1 rule 2), so Night is the heavier pass.
- [ ] **Viewport.** DevTools device toolbar, *Responsive*, **390 × 844**, device pixel ratio 3, mobile UA on, no touch emulation needed. Do not pick a named phone preset: presets change the UA client hints and, on some, the DPR.
- [ ] **CPU.** Performance panel → capture settings (the gear) → **CPU: 4× slowdown**. Network: *No throttling* (everything is cached; a network throttle would hold the chunk loads, which happen *before* a turn starts — §6.4 starts the View Transition at module resolve — and are not part of the measurement).
- [ ] **Panel options.** Screenshots on (to see the wipe), *Web Vitals* lane off, *Enable advanced paint instrumentation* **off** (it inflates main-thread time), memory off.
- [ ] **Quiet tab.** Close other tabs, pause extensions (or use a guest profile), plug the laptop in, and let the page idle ten seconds after the reload before recording.

## 3. The two extra moments

- [ ] **The Dojo arrival (moment A, §7 A).** With the save loaded and the shell cached, start recording, reload at `#/`, and let it settle: the boot ensō draws (`--dur-4`), `store.ready` flips with the Dojo chunk prefetched, and `App` runs the arrival View Transition carrying `enso` from `.app-loading__mark` onto `.dojo-scene__art`; the phase word, the tategaki column and the since-yesterday pulse follow (B1). Measure from the first frame of the ensō to the end of the last entrance. A cold reload (service worker cleared) is a different measurement and is not this protocol.

## 4. Recording and reading the trace

1. Open DevTools → **Performance**. Confirm the gear shows *CPU 4× slowdown*, *Network: No throttling*.
2. Press **Record** (⌘E / Ctrl+E), wait one second, perform the turns of §2 with two-second pauses, then **Stop**. Save the trace (right-click the timeline → *Save profile…*) as `trace-<phase>-<theme>-<commit>.json` outside the repo; traces are not committed.
3. For each turn, select the window from the input event (the *Interactions* lane shows the tap / click) to the end of the last animation frame after it — about `--dur-3` 400 ms plus settle; `in` and `out` turns are 300–400 ms, the dusk wipe 400 ms, the arrival up to about 2.5 s.
4. **Frames.** In the *Frames* lane, hover each frame inside the window: read its duration. Partially presented frames are hatched, dropped frames red. **Any frame over 18 ms fails the turn.** Record the longest frame per turn.
5. **Long tasks.** On the *Main* track, a task longer than 50 ms carries a red hatched corner. **Any long task inside a turn's window fails the turn.** Record its duration and its bottom-up top entry (Summary → *Bottom-Up*): layout, paint, style recalc or script, and which function.
6. **Paint cost.** Open *Layers* or tick *Enable advanced paint instrumentation* only for a diagnosis pass, never for the recorded run.
7. Repeat the whole set in the other theme. Record the worst of both.

What usually fails, and where the spec already names the owner: a frame that recalculates style for the whole page (the sekki tint *steps*, §7 H; a `color` transition on a background over 160 px breaks §6.7 rule 1); a `filter` or `box-shadow` that animates (§1 rule 2); more than two live SVG filters in the viewport (§6.7 rule 2); `backdrop-filter` on the header during a transition (`Layout.css` rests it under `html:active-view-transition`); `restoreScroll()` before paint (§6.7 rule 6).

## 6. Headless stand-in (2026-10-18)

What was actually run, so the §5 rows can be read for what they are. Scripts and traces live outside the repo in the session scratchpad (`…/scratchpad/frame-protocol/`: `save.mjs`, `run.mjs`, `parse.mjs`, `trace-light.json`, `trace-dark.json` ≈ 73 MB each, `log-*.json`, `parsed-*.json`); nothing was added to the repo but this section and the rows above, no dependency was installed, no commit made.

- **Browser and driver.** Chrome 156.0.8078.36 (`Browser.getVersion`: `Chrome/156.0.8078.36`, V8 15.6.75.16) launched as `--headless=new --remote-debugging-port --user-data-dir=<fresh empty dir per theme>`, driven over the DevTools Protocol from a Node 26 script using the built-in `WebSocket` and `fetch` — no puppeteer, no playwright. `Emulation.setDeviceMetricsOverride` 390 × 844, DPR 3, `mobile: true`; `Emulation.setUserAgentOverride` to a mobile Chrome 156 UA; `Emulation.setCPUThrottlingRate` 4; no network throttle. `document.startViewTransition` was present and every turn ran under it (`html[data-travel]` read at `vt:start`: forward / forward / back / forward / forward / home / in / out / forward / home; the wipes `data-vt="theme"`).
- **Build and cache.** The integrator's production `dist/` (HEAD `bc6b8e8` + the Phase C working tree, not rebuilt) served by `npx vite preview --port 4173 --strictPort` (it binds `[::1]:4173`, so the page was `http://localhost:4173/#/`). First load → wait for the worker (`activated` and `navigator.serviceWorker.controller`), then two reloads so the shell, `assets/**`, `calendar/koyomi.json` and the three first-paint fonts (plus `ShipporiMinchoB1-base`) came from the worker's caches; then the 4× throttle and a 10 s idle before `Tracing.start`.
- **Save.** Seeded into `localStorage` before the first boot (`Page.addScriptToEvaluateOnNewDocument`, keys from `src/store/persist.ts`): `tsuzuku.meta.v1` — a learner at 34 training days, streak 32 (lit: `lastDay` = yesterday), two 氷 freezes, five badges, three stamps, one wallpaper, station 4 (Yellow) with 1–3 cleared, `onboardedAt` set, 34 `daily` rows, 4,300 XP, `reducedMotion: false`, `theme: 'light'` for the Morning pass and `'dark'` for the Night pass; plus two card shards (`tsuzuku.cards.v1.kana.kana` 238 kana `#rec` cards, `tsuzuku.cards.v1.vocab.n5` 80 vocab `#rec` cards, ~30 due today). `migrations.fillMeta` accepted it unchanged (station 4, freezes 2, 12 badges after the unlock reducer ran). `arrivedDay`, `sceneSeen` and `stationSeen` were left absent, so the Tōchaku (§7 D) played on turn 1's Road and the arrival played on the first load.
- **Turns.** Real input where the table says tap: `DOM.getBoxModel` centre of `.layout__nav a[data-nav=…]`, `.tokaido__station[aria-current="step"]`, the one `.layout__main .hanko` (Shugyō, the recommended session), `.train__begin`, `.session__leave`, `.session__leave-keep`, `input[data-setting="theme"][value=…]`, then `Input.dispatchMouseEvent` pressed / released; turn 3 was `history.back()`. **Turn 8 is *Leave* mid-session** (Begin → first step → Leave → “Keep my place and leave”): a plain `out` turn with the shiori slip, not the End Card's **Rest.** with the `tsuzuku-mark` hero — a finished Shugyō was not driven. ≈ 2 s between turns (3.5 s after turn 1 for the Tōchaku). Each `startViewTransition` was wrapped before boot to `performance.mark` `vt:<n>:start / ready / finished`, and `pointerdown` was marked, so every window is read from the trace, not from wall-clock guesses.
- **Trace and reading.** One `Tracing.start` per theme (`devtools.timeline`, `disabled-by-default-devtools.timeline`, `disabled-by-default-devtools.timeline.frame`, `toplevel`, `v8.execute`, `blink.user_timing`, `loading`; `ReturnAsStream`). Per turn: the window runs from the `pointerdown` mark (the turn mark for `history.back()`) to `vt:finished` + 400 ms settle. **Frames** are the gaps between successive compositor `DrawFrame` events of the page's renderer inside the View Transition span `[vt:start, vt:finished]`, the first gap counted from `vt:start`; the tap → `vt:start` wait (12–45 ms, 126 ms on turn 1) is the chunk load / page build §1 excludes and is not a frame here. **Long tasks** are outermost main-thread `RunTask` > 50 ms overlapping the whole window, with the top self-time child read from the nested events (the trace carries no sampled stacks). The dusk wipes are read the same way; the arrival from the reload's `firstContentfulPaint` (the ensō's first frame) to +2.5 s.
- **Caveats, honestly.** (1) Headless Chrome rasterises and composites in software: a frame here includes software raster of the snapshot layers at DPR 3, which a phone's GPU does not pay — the frame numbers are pessimistic and are *not* the DevTools *Frames* lane. (2) The 4× throttle applies to the renderer only, as in DevTools. (3) The arrival's `enso` View Transition never ran in this environment (three loads, throttled and not): the Dojo chunk resolved after `store.ready`, so `App` took the plain arrival; the figure measures the DojoPage entrances only. (4) The 93 / 82 ms task on turn 1 is the once-per-visit audio unlock on the first gesture (`src/audio/tts.ts`), not Road or Station work; in a manual run it lands on whatever is tapped first, and a tester who taps once before recording would not see it. (5) The hearth's `dj-hf-flicker` (`src/art/dojo/flames.ts:253`, `1.6s … infinite`, `transform: scale` on the flame paths) keeps the compositor presenting 60 frames/s for as long as the hearth is in view (517 frames in the 8.6 s after the arrival window with 7 style recalcs and 15 paints on the main thread) — a compositor-only cost, allowed by `motion.test`'s ≥ 1,400 ms rule for infinite animations, noted here because it is what an idle Dojo costs. (6) `document.getAnimations()` on the Dojo after the arrival showed the §7 A choreography as specified (brand `tomosu` 900 ms, phase word nijimi at +600 ms, six column items staggered 40 ms from +640 ms, the status window at +1,240 ms).
